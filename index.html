01The division of responsibility

Settled in conversation with the product owner:

ConcernSystemSubjectIdentity
Officer duty-area containmentBubo (exists today)OfficersNamed, consented, contract-governed, GPS-tracked
Breach detection on high-risk spotsRuView (to build)Unknown contactsPseudonymous, deliberately unbindable
Correlating the twoNew layer—Join at the incident layer only

RuView is a cueing sensor, not an identification system. It answers "did something cross this boundary, inbound, at what bearing, with what confidence." It cannot answer "who." That is structural: ruview-track pseudonyms have no field that can bind to a civil identity (ADR-307 invariant 1), and adding one would convert a privacy-preserving sensing system into unconsented surveillance.

Therefore: never ask RuView who the person is. Ask Bubo whether anyone was authorised there, and correlate. See §5.

03The gap RuView still has

There is no polygon anywhere in RuView's Rust code. ruview-placement is axis-aligned Rect only. A perimeter, a guarded sector, and a high-risk spot are all polygons. The kernel exists only as JavaScript in sitelift-watchfloor.html §1, with a Rust port spec in ADR-325-P1-geometry-kernel-spec.md.

Three traps in that spec, each observed rather than theorised — read §6 of it before implementing:

  1. Boundary classification is arbitrary. Point (70,10) exactly on a fence edge returns contains == true; (150,45) exactly on a vertex returns false. Even-odd ray casting is undefined on the boundary — which is where a perimeter detector lives. Use three-way classify(p, tol).
  2. Two control points always fit perfectly, so a reported fit_residual_m of 0.0 is meaningless. Must be Option<f64> / None.
  3. Derived sector bands can self-intersect on concave corners, producing a silently dead sector.

05The correlation design

5.1 · Expected-presence deconfliction

  • Bubo: officer at (lat, lon) at time T, accuracy radius r
  • RuView: unattributed contact at (lat, lon) at time T, uncertainty radius u
  • Footprints overlap in space and time → attributable to a known officer
  • No overlap, with good officer data → that is the breach

RuView still only emits "unknown contact." Attribution happens above it. Nothing is written back into the pseudonym space.

5.2 · The four invariants

Implemented and tested in deconfliction.js:

  1. Never suppress, only downgrade. No code path discards a detection.
  2. Fail toward alarm. Missing, stale, or coarse officer data → INDETERMINATE, which alarms. Absence of an officer record is not evidence the contact was an officer.
  3. Coarse fixes cannot attribute. A 200 m GPS fix geometrically overlaps an entire site and would excuse every breach on it. Reject above maxAccuracyM (default 25 m).
  4. Ambiguity escalates. Two candidate officers, or person_count above the number of overlapping officers, → AMBIGUOUS. This is the "intruder standing next to the officer" case.

5.3 · Attribution is not authorization

Two separate questions, two owners:

VerdictMeaningOwnerAlarms
UNATTRIBUTEDGood data, nobody matched. Strongest intruder signalRuView incidentyes
ATTRIBUTED_AUTHORIZEDOne on-duty officer overlaps, permitted here—no
ATTRIBUTED_UNAUTHORIZEDOfficer overlaps but outside their duty areaBubo containmentyes
AMBIGUOUSMultiple candidates, or count mismatchescalate to humanyes
INDETERMINATENo usable officer data — deconfliction was blindRuView incident, flagged blindyes

ATTRIBUTED_UNAUTHORIZED is the bridge between the two products: it is not a RuView intrusion, it is a Bubo geofence violation surfaced by a RuView sensor.

5.4 · Two honest problems

Indoor GPS breaks correlation exactly where RuView matters most

Outdoor GPS is 3–5 m; indoors it is unusable. RuView's differentiator is camera-free indoor sensing, so the officer's position goes dark in precisely the monitored spots. Consequence: with GPS only, deconfliction is an outdoor-perimeter-only feature, and indoor detections must be treated as INDETERMINATE — i.e. they always alarm. That may be acceptable, but it must be a decision, not a surprise. Mitigation depends on B3.

If Bubo has no accuracy field (B2), do not ship attribution

Without a per-fix accuracy, invariant 3 is unenforceable and a bad fix will suppress a real breach. Better to ship cue-only (§6) than to ship a suppressor that fails silently.

06Ship cue-only first

Recommended sequencing, and this is the important recommendation in this document: build the patrol-cue path before deconfliction.

  • It requires no attribution at all. Any unattributed contact → dispatch a patrol to clear it. The officer arriving is expected.
  • It matches RuView's evidence grade. Events are L1 heuristic with no certified accuracy. Sending a human to look is the correct authority for an L1 signal; locking a gate or calling police off an unvalidated sensor is not.
  • The policy gate already encodes the distinction: in the prototype, "Dispatch patrol to sector" is ActionClass::Safety while "Lock Gate B" is Security — the latter requires a KNOWN domain plus a valid certificate and fails closed.

Deconfliction then becomes an optimisation that reduces nuisance dispatches, not a prerequisite for shipping.

7.2 · What to add

A simulated Bubo officer feed.

// One officer per patrol guard, plus optional roamers.
// Deterministic: derive jitter from the seeded PRNG, never Math.random.
function buboFixFor(guard, simMs, rand) {
  const indoor = SITE.spaces.some(sp => Geom.contains(rectPoly(sp.rect), guard.p));
  // THE KEY BEHAVIOUR: GPS accuracy collapses indoors.
  const accuracy_m = indoor ? 45 + rand() * 120 : 3.5 + rand() * 3;
  const dropout = rand() < (indoor ? 0.35 : 0.02);
  if (dropout) return null;                     // feed gap ⇒ INDETERMINATE
  const jitter = accuracy_m * 0.4;
  const w = SITE.frame.enuToWgs84([
    guard.p[0] + (rand() - 0.5) * jitter,
    guard.p[1] + (rand() - 0.5) * jitter
  ]);
  return {
    officer_id: "off_reyes",
    at_unix_ms: 1755400000000 + simMs,
    lat: w.lat, lon: w.lon,
    accuracy_m: +accuracy_m.toFixed(1),
    source: "gps",
    on_duty: true,
    authorized_zones: SITE.patrol.checkpoints.map(c => c.id)
  };
}

Run every detection through deconflict() before it opens an incident, and render the verdict on the event and on the map (colour the contact by verdict, draw the officer's accuracy circle so the operator sees why a suppression happened).

Add a fail-open toggle, defaulted off

A switch that makes missing officer data suppress instead of alarm — so a reviewer can watch scenario 3 silently swallow a breach, then switch it back. Making the wrong behaviour demonstrable is the fastest way to get the invariant respected. Label it clearly as a demonstration of a defect, not a configuration option.

7.3 · UI additions

  • Verdict pill on each event, coloured: UNATTRIBUTED breach-red, AMBIGUOUS violet, INDETERMINATE violet outline, ATTRIBUTED_AUTHORIZED clear-sage, ATTRIBUTED_UNAUTHORIZED ochre
  • Officer accuracy circle on the map, dashed, with the metre value

08What must not happen

Non-negotiables carried from ADR-325 and the RuView repository rules:

  1. No officer identity in the sensing pseudonym space. Correlation output lives in the incident record. ruview_ontology::Track/Person never gain an officer field.
  2. No suppression. Downgrade only. There must be no code path that drops a detection because an officer might have caused it.
  3. No fabricated confidence. Where observability is degraded, emit UNKNOWN — never a plausible-looking low number.
  4. No MEASURED labels without a reproducer on real silicon. Everything in the emulation is SYNTHETIC / L0; deconfliction verdicts over simulated feeds are SYNTHETIC too.
  5. No pose-accuracy claims. The shipped image has no weights and returns keypoint confidence 0.0.
  6. Officer position is consent-governed data. The joined correlation record inherits the stricter of the two retention regimes (B7). Do not persist officer tracks into RuView's evidence ledger without answering that.

10.2 · The accuracy field has opposite risk polarity in the two systems

This is the most important structural finding.

Bubo containmentRuView deconfliction
DecisionIs the officer INSIDE?Does this contact overlap a known officer?
Large accuracySafer — bigger tolerance buffer, fewer false "outside"Dangerous — overlaps everything, suppresses real breaches
Small/zero accuracyDangerous — buffer collapses to a point, boundary fix reads OUTSIDE (C2.2)Safer — no spurious overlap

The same field, read the same way, fails in opposite directions. Bubo's accuracy handling cannot be reused for RuView deconfliction — the safe direction inverts. Invariant 3 (maxAccuracyM) is correct for RuView and would be actively wrong as a Bubo containment rule.

Fixed in code: accuracy_m <= 0 is now rejected as accuracy_zero_or_negative, because per C2.2 a zero means accuracy unknown in this pipeline, not perfectly precise.

10.3 · The staleness guard was defeated — invariant 2 needed a second mechanism

BUBO-GEO-STALECOORD-001 (severity High, root cause confirmed in source):

  • logGeoClockInTrack uses _lastLocation ?? getCurrentLocation() — a fresh fix runs only if the cache is null (location_service.dart:641,652)
  • _lastLocation is assigned in three places and never cleared, on a singleton service (:246,366,472)
  • While clocked out, isTrackingEnabled is false so onLocation early-returns — the cache is guaranteed stale at the next clock-in (:139-149,221-225)
  • location_service.dart:394 stamps the ping with DateTime.now() even though the coordinate is old — "the record LOOKS current, so staleness is invisible downstream"

That last line is fatal to a timestamp-based freshness check. §5.2 invariant 2 relied on at_unix_ms skew; a frozen coordinate from a previous shift arrives with a perfectly fresh timestamp and passes maxTimeSkewMs cleanly.

Fix implemented: frozen-coordinate detection by movement

With cfg.priorFixes[officer_id], a fix that has moved ≤ frozenEpsilonM (0.5 m) over ≥ frozenMinElapsedMs (60 s) is rejected as frozen_coordinate. Tests cover the frozen case, the genuinely-moved case, and — deliberately — the blind case: without priorFixes the defect is undetectable, and there is a test asserting exactly that so the blind spot is visible rather than assumed away.

Consequence for sequencing

Until BUBO-GEO-STALECOORD-001 is fixed, attribution rests on a feed with a confirmed high-severity staleness defect whose own timestamps cannot be trusted. That strengthens §6 considerably — ship cue-only. A suppressor built on this feed can silently excuse a real breach using a coordinate from a previous shift at a different post.

10.4 · Bubo has RuView P1's polygon trap, confirmed in production

C1.3 [CONFIRMED]:

A self-intersecting polygon, fewer than 3 vertices, or wrong winding produces wrong intersects() results. determine_geofence_status checks polygon.is_valid but only logs a warning and proceeds — no .buffer(0) repair, no bail-out (calculate_geofence_status.py:67-77).

This is trap 3 in ADR-325-P1-geometry-kernel-spec.md §6, occurring in a live system. It also names wrong winding, which is precisely why the P1 spec canonicalises every ring to CCW on construction (invariant I1/I3) instead of trusting input order.

So the P1 kernel should not adopt Bubo's polygon handling. It should reject invalid rings with a typed error, and it is a candidate to replace Bubo's validation rather than mirror it — a shared, strict kernel would close C1.3 on the Bubo side too. That reframes the "reuse Bubo's polygon?" question in §9 action 2: the answer is likely the other direction.
